# R0.6 正式决定与行动开始条件增量

状态：基于 R0.5 的合成数据后端闭环；不是现实社区授权，也不是完整 R1。

## 目标

本增量把“表达立场”“按登记资格批准决定”“本人接受任务”“确认行动可以开始”拆成四种不同事实：

1. 立场继续只用于理解讨论；
2. 管理员为特定议题登记批准资格，不从账号角色自动推断；
3. 主持人冻结决定版本、规则版本、至少两名必需批准者及必需任务；
4. 决定生效后，仍须等必需任务由本人接受、资源条件核实，才能单独开始。

所有样本继续明确标记为合成开发记录。程序不能决定现实中谁有批准资格；真实资格和替补规则必须由有权社区主体另行确认。

## 纳入范围

- 议题范围的批准资格登记与撤销；
- 绑定具体方案版本的决定草稿；
- 生效条件、资源条件及主持人逐项核实；
- 冻结规则版本、决定版本、必需批准者和必需任务；
- 至少两名不同批准者逐人批准；
- 最后一次批准时重新检查账号、资格版本、条件及全部批准；
- 资格撤销使待批准决定进入 `blocked`，清除旧批准；主持人须提交新规则快照，所有人重新批准；
- 决定 `effective` 与行动 `started` 分离；任务未由受邀者本人接受或资源条件未核实时禁止开始。

## 明确不交付

- 不提供真实社区批准者默认名单、法定表决、代理投票、回避规则或纸面批准代录；
- 不实现决定正文修订、取代、撤销、重议及历史版本比较；
- 不实现任务条款变更、重新接受、执行、核验和复盘；
- 不提供本轮前端 UI；接口用于合成合同与后续界面开发；
- 不把管理员、主持人、支持立场、理解准确、分享内容或任务邀请自动转成批准；
- 不把通过测试解释为现实决定有效。

## 验收

- 一名批准者、普通成员、支持立场或未回应均不能使决定生效；
- 两名冻结批准者对同一版本批准且生效条件齐备，才在同一事务变为 `effective`；
- 第一名批准者随后失去资格时流程变为 `blocked`，旧批准不能复用；
- 新规则快照必须使全部批准重新发生；
- 决定生效但必需邀请尚未接受或资源未确认时，开始接口返回 `422`；
- 本人接受任务且资源条件齐备后，主持人才能把行动变为 `started`；
- 权限、版本、幂等、对象归属和 R0.5 恢复就绪检查继续生效。
